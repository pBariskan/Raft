§ 01

Chaos testing

The whole cluster runs inside a deterministic simulator: virtual time, a network that delays, loses and splits messages, servers that crash and reboot from their simulated disks. One seed decides everything, so any failure replays exactly.

A chaos run is 3,000 ticks of random faults from one of five profiles (steady, churn, flaky network, slow storm, reboot storm) while five clients send GET, PUT, APPEND and DELETE on two keys. Then every fault is removed and the cluster must recover: every client answered, a final write on every server. Election Safety, Leader Completeness, State Machine Safety and Log Matching are checked on every step; the client history is checked for linearizability with Porcupine at the end.

§ 02

Testing the tests: six classic mistakes

Zero violations only means something if the checks can fail. So six well-known Raft mistakes can be switched back on, and each must be caught. Each row is 1,000 seeds with that one mistake on; “watch” replays the first failing seed in the Workplace, tick by tick.

§ 03

What the testing found

No bug in the Raft core has been caught so far (the running list is docs/bugs.md). What the chaos runner did find were weaknesses in the tests themselves, while tuning them to catch the mistakes above:

Figure 8 was invisible because of the no-op

A new leader's no-op means every acknowledgement also covers a current-term entry, so counting old entries never changed a commit decision. The mistake switch now also drops the no-op. Even then it needs rare timing: 2 of 1,000 seeds.

One “classic mistake” turned out harmless

“Follower trusts the leader's commit index” couldn't break anything here, because every AppendEntries carries the leader's whole missing suffix, so the commit index never exceeds what the message verified. It was replaced by “accept entries from a stale leader”, which does break things.

Forgetting a vote needs reboots mid-election

Steady fault profiles never caught it. A “reboot storm” profile, crashing and restarting servers constantly, does.

PUT hides duplicates

Applying PUT x=5 twice looks like applying it once. Adding APPEND to the workload, which is not idempotent, made missing duplicate detection visible to the linearizability check.

§ 04

Real servers: benchmarks

The same Raft core runs as real servers: a 10 ms tick, a checksummed write-ahead log synced with fsync before any reply, and HTTP between processes. cmd/bench runs a cluster over loopback and measures writes (every request goes through the log).

§ 05

How it's built

raft/ roles, terms, votes, the log, the commit rule. No clock, no network, no disk: told “a tick passed” or “this message arrived”, it answers with what to save, send and apply.
sim/ virtual time and an unreliable network. Tests, chaos runner, this site.
server/ real time, files with fsync, HTTP. raftd, the benchmark.
kv/ the key-value state machine and client sessions, on either.
wasm/ + play/ the simulator compiled to WebAssembly for these pages.

The order of a server's loop is the whole safety story: save and fsync, then send, then apply and answer.

raft/
The algorithm, about 600 lines, deterministic.
sim/
Simulator, clients, chaos runner, the safety checks, classic mistakes.
check/
Linearizability via Porcupine, per key.
kv/
GET, PUT, DELETE, APPEND; duplicate detection by client ID and sequence number.
storage/, transport/, server/, client/
Real mode: write-ahead log, HTTP, the server loop, a client that follows leaders and retries.
cmd/
chaos, raftd, cluster, bench.
web/
This site: plain HTML, CSS and JavaScript around the WebAssembly engine.

§ 06

Run it yourself

git clone https://github.com/pBariskan/Raft && cd Raft
go test ./...                              # every test, including 300 chaos seeds
go run ./cmd/chaos -seeds 1000             # the chaos runner
go run ./cmd/chaos -mistake forget-vote    # watch a classic mistake get caught
go run ./cmd/cluster -n 5                  # five real servers; kill and restart them from a prompt
scripts/serve-web.sh                       # this site on localhost:8080
